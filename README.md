# kubernetes-100year-binary

Builds `kubeadm` binaries whose **default certificate validity is 100 years** (upstream ships 1 year for
leaf certificates and 10 years for the CA), one branch and one release per Kubernetes release.

- Upstream: [kubernetes/kubernetes](https://github.com/kubernetes/kubernetes)
- Releases: [github.com/xuxiaowei-com-cn/kubernetes-100year-binary/releases](https://github.com/xuxiaowei-com-cn/kubernetes-100year-binary/releases)
- Coverage: `v1.24.0` … `v1.37.1` — every official Kubernetes release in that range

## Background

Certificates generated by `kubeadm init` expire after one year (the CA after ten), which means a cluster
needs `kubeadm certs renew` on a schedule. This project patches the validity constants at compile time, so
a cluster initialised with these binaries gets 100-year certificates out of the box.

Only `kubeadm` is built and published here.

## Download and install

From the Releases page (example: `release-v1.37.1`, replace the architecture as needed):

```shell
curl -LO https://github.com/xuxiaowei-com-cn/kubernetes-100year-binary/releases/download/release-v1.37.1/kubeadm-amd64
chmod +x kubeadm-amd64
sudo install -m 0755 kubeadm-amd64 /usr/bin/kubeadm
kubeadm version
```

Release assets are named `kubeadm-<arch>`:

| Architecture    | Asset             | Available for              |
|-----------------|-------------------|----------------------------|
| `linux/amd64`   | `kubeadm-amd64`   | all versions               |
| `linux/arm64`   | `kubeadm-arm64`   | all versions               |
| `linux/ppc64le` | `kubeadm-ppc64le` | all versions               |
| `linux/s390x`   | `kubeadm-s390x`   | all versions               |
| `linux/arm`     | `kubeadm-arm`     | `v1.24.x` – `v1.26.x` only |

## Bulk download

[`scripts/download-releases.sh`](scripts/download-releases.sh) downloads every release asset into
`<output-dir>/<version>/<arch>/kubeadm`, verifies the SHA-256 of files that already exist against the digest
published with each release asset, re-downloads on mismatch, and writes `SHA256SUMS` per version.

```shell
# everything into ./releases -> ./releases/v1.37.1/amd64/kubeadm
./scripts/download-releases.sh -d ./releases

# behind a slow GitHub connection, prefix the asset URL with a proxy
./scripts/download-releases.sh -d ./releases --proxy https://gh-proxy.org/ --log download.log

# verify only, never download (falls back to the local SHA256SUMS if the API is unreachable)
./scripts/download-releases.sh -d ./releases --verify-only

# other switches
./scripts/download-releases.sh --list --version-regex '^v1\.3[0-7]\.'   # dry run
./scripts/download-releases.sh --arch arm64 -j 8                        # one architecture, 8 parallel
./scripts/download-releases.sh --force                                  # ignore existing files
```

Verify a version directory offline:

```shell
cd releases/v1.37.1 && sha256sum -c SHA256SUMS
```

## How the CI works

[`.github/workflows/build.yml`](.github/workflows/build.yml) runs on pushes to branches `v*`, on tags
`release-v*`, on pull requests and on manual dispatch:

1. Resolve `K8S_VERSION` from the ref (`v1.24.0` or `release-v1.24.0` → `v1.24.0`).
2. `git clone --branch "$K8S_VERSION" --depth 1` from `kubernetes/kubernetes`.
3. Apply the 100-year certificate patches.
4. `apt-get update && apt-get install -y rsync`.
5. `make all WHAT=cmd/kubeadm` with `KUBE_BUILD_PLATFORMS` set.
6. Binaries land in `kubernetes/_output/local/bin/linux/<arch>/kubeadm`.
7. Branch push → artifacts are uploaded. Tag push → a GitHub Release is created with the `kubeadm-<arch>` files
   (prerelease versions are not tagged in this repository).

### The 100-year certificate patch

| Version               | Patch                                                                                                                                                                                                                                                                                                              |
|-----------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `v1.24.0` – `v1.30.x` | `staging/src/k8s.io/client-go/util/cert/cert.go`: `duration365d * 10` → `duration365d * 100`<br>`cmd/kubeadm/app/constants/constants.go`: `CertificateValidity = time.Hour * 24 * 365` → `time.Hour * 24 * 365 * 100`                                                                                              |
| `v1.31.0` and later   | same `cert.go` patch, plus `cmd/kubeadm/app/constants/constants.go`: `CACertificateValidityPeriod` (`* 24 * 365 * 10` → 100 years) **and** `CertificateValidityPeriod` (`* 24 * 365` → 100 years), plus commenting out both `notAfter = cfg.NotAfter` assignments in `cmd/kubeadm/app/util/pkiutil/pki_helpers.go` |

`v1.31.0` renamed `CertificateValidity` to `CertificateValidityPeriod`, added a separate CA constant and moved
CA creation into kubeadm itself; it also lets `ClusterConfiguration.certificateValidityPeriod` /
`caCertificateValidityPeriod` override the compiled default through `cfg.NotAfter`, which is why the later
branches disable that override so the 100-year value always wins.

### Build container

`container` is the Go version that release requires — `golang: <golang: upstream version>` from
`build/dependencies.yaml`, or `.go-version` for `v1.35.0` and later.

Watch the image base: `apt-get install -y rsync` fails inside some bullseye-based images (`golang:1.18.x`,
`golang:1.20.3`, `golang:1.20.4`), so `v1.24.x` uses `golang:1.19.13` and `v1.27.0`–`v1.27.2` use
`golang:1.20.5` (bookworm) instead of the exact version listed upstream.

### Platforms

`KUBE_BUILD_PLATFORMS` mirrors `KUBE_SUPPORTED_SERVER_PLATFORMS` in the upstream `hack/lib/golang.sh`.
Upstream dropped `linux/arm` in `v1.27.0`, so those branches build and publish four platforms only.

## Maintenance

Adding a new Kubernetes release:

1. Check upstream: the Go version required by `build/dependencies.yaml` / `.go-version`, the platform list in
   `hack/lib/golang.sh`, and whether the patch anchors above still exist.
2. Branch from `v1.24.0`, then adjust the container, the platform list and the patch steps for that release.
3. Commit (`:gitmoji:` prefix, `Signed-off-by` DCO sign-off) and tag it `release-vX.Y.Z`.
4. Push: branches can be pushed in one batch, **tags must not**.

### Pushing tags

GitHub does not create workflow runs when a single push creates **more than three tags**, so a bulk
`git push origin --tags` silently produces no builds
([community discussion](https://github.com/orgs/community/discussions/56152)). Push tags in batches of at
most three, or dispatch the workflow for tags that are already on the remote:

```shell
git push origin release-v1.37.0 release-v1.37.1     # at most three tags per push
gh workflow run build.yml --ref release-v1.37.0     # trigger one tag without re-pushing it
```
